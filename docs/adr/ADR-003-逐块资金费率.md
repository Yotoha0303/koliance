# ADR-003：资金费率采用「逐块结算 + 有界可调速率」

- **状态**：已决定 —— **逐块惰性结算**，速率是 owner 可调参数（有硬上限）
- **日期**：2026-10-07
- **触发**：`docs/前沿资讯与竞品分析.md:32-36`（Metropolis Track 1 官方样例含
  "perpetuals whose funding refreshes each block"）、同文 `:294`（"剩下的空位"）
- **影响范围**：`contracts/contracts/perp/`（`PositionManager.sol` / `PerpConstants.sol` / `IPositionManager.sol`）、
  `src/lib/perp.ts` / `src/lib/perpConfig.ts`
- **分支**：`feat/perp-solvency-and-panel`

---

## 1. 决策

**资金费率按区块累积、惰性结算；速率默认取现实值，但作为 owner 可调参数存在，上限 1e13 WAD/块。**

三条具体规定：

1. **累积方式**：`cumulativeFundingIndex[feedId]` 按块累加，
   `delta = elapsed × rate × skewWad / WAD`，其中
   `skewWad = (longOI − shortOI) / (longOI + shortOI) × WAD`。
2. **结算方式**：头寸存 `entryFundingIndex`，应付额为
   `signedSize × (indexNow − entryFundingIndex) / WAD`，**O(1)**，与经过多少块无关。
3. **速率**：默认 `1e11`（≈0.86%/天，1 秒出块），owner 可在 `[0, 1e13]` 内调整。

---

## 2. 为什么是「逐块」

常规永续每 1–8 小时结算一次资金费。这是**吞吐量的妥协**，不是机制上的必然：
收敛基差的套利受限于资金费能多快被收取。

- 8 小时结算 → 套利者一天只有 3 次机会
- 逐块结算 → 一天约 86,400 次机会

出块越快，永续越贴近现货。这是**高吞吐链能做、慢链做不到**的事，
也正好是 Track 1 官方样例点名要的方向。所以选它不只是"加个功能"，
是让项目的核心叙事从"性能展示"（批量清算）升级为"机制创新"。

---

## 3. 备选方案与被否理由

| 方案 | 做法 | 否掉的理由 |
| --- | --- | --- |
| **A. 逐块惰性累积（本决策）** | 索引 + 每笔交易进入时先累积 | —（采用） |
| B. 逐块 + keeper 定时调用 | 独立进程每块调 `accrueFunding` | **引入外部依赖**。惰性累积已经能做到逐块（哪笔交易先来就先累积），keeper 只是把"能跑"变成"必须有人跑"。演示时 keeper 挂了就是资金费停摆。 |
| C. 每 8 小时一次（传统） | 定时结算 | 放弃了本项目的核心叙事。官方样例明确点名逐块。 |
| D. 逐块 + 把未结算部分逐笔写入 storage | 每次累积遍历所有头寸更新余额 | **gas 无上界**。头寸数没有上限，遍历会让开平仓成本随头寸数增长。索引法把结算推迟到平仓那一刻，O(1)。 |
| E. 只算速率、不真正结算 | 展示用假数据 | 违反纪律 §1「读到才算」。而且 `isLiquidatable` 就不含资金费，与真实行为不一致。 |

---

## 4. 为什么速率必须是参数（本决策最容易被质疑的一点）

**算术事实**：`1e11 WAD/块` 在满偏斜下，对 9,990 USD 的头寸是
`9990 × 1e-5 = 0.0999 USD/块`（按 `1e11/1e18 = 1e-7` 计）——
**准确，但在几百块的演示里完全看不出来。**

实测（`contracts/test/perp/Funding.ts`）用的是 `1e13`，即 1e-5/块，
这样 1,500 块能累积出 400+ USD，足以单独触发清算。

于是存在一个**真实的两难**：

| 选择 | 后果 |
| --- | --- |
| 用现实速率 | 演示里资金费纹丝不动，评委看不到机制 |
| 用演示速率 | 数字好看，但是假的——不能对外宣称是"现实参数" |

**本决策的解法：不选，而是把它变成参数。** 默认值是现实值（诚实），
演示部署把它调高（可见）。机制完全相同，只有算术尺度不同。

**代价与护栏**：
- owner 可以把速率调到伤害用户的程度 → 因此设 `MAX_FUNDING_RATE_PER_BLOCK_WAD = 1e13` 硬上限。
  1e13 已是约 86%/天，远超任何真实场所；上限的存在是为了让"演示档"不能变成"抽干抵押品"。
- 改速率**不追溯**已累积的部分（索引已经落账），只影响未来区块。这是保守方向。
- 治理应该**收紧**这个上限，不是放宽。

## 5. 资金费进入清算判定（关键设计）

`_isLiquidatable` 的权益是 `collateral + pnl − funding`，**下限截断在 0**。

含义：**满偏斜的一侧可以仅因持仓成本被清算**，价格不动也会爆。
这是逐块资金费真正"咬人"的地方——8 小时费率做不到这一点，
因为它一天只咬 3 次，每次的量被套利抹平。

顺序必须严格是 `collateral + pnl − funding` 再截断：
- 先截断 pnl 再减 funding → funding 会"复活"一个已破产的头寸，既错又可被利用
- 忘了加 `collateral` → 权益凭空少一个抵押品（**本次实现中真实犯过这个错，被测试抓到**）

---

## 6. 符号约定

```
index 上升 ⟺ 多头占优 ⟺ 多头付费
应付额 = signedSize × (indexNow − entryFundingIndex) / WAD
         其中 signedSize = +size（多） / −size（空）
正数 = 交易者付，负数 = 交易者收
```

**为什么需要 `signedSize` 而不是只靠索引方向**：只用索引方向的话两侧会被收同样的费，
空头永远收不到钱——资金费就变成了"手续费"而不是"两侧之间的转移"。
（**这也是本次实现中真实犯过的错，被 `Funding.ts` 的"short must be paid"用例抓到。**）

---

## 7. 重新评估的触发条件

- 若引入**逐块预言机**（每块强制喂价），惰性累积应改为在喂价入口累积，避免无人交易时索引停滞；
- 若支持**多个抵押品 / 跨保证金**，`skewWad` 需要按抵押品分组，否则不同抵押品的头寸会互相计费；
- 若监管要求**可预测的持仓成本**，应改为固定周期结算并提供预告期，而不是 owner 可调。

## 8. 验证方式

`contracts/test/perp/Funding.ts`，18 条，全部实测通过。核心断言：

| 性质 | 用例 |
| --- | --- |
| 平衡账本不再累积 | `accrues nothing further when long and short open interest are equal` |
| 平衡后双方义务不再增长 | `stops growing either side's obligation once the book is balanced` |
| 拥挤侧付费、稀薄侧收钱 | `charges the crowded side and pays the thin side` |
| 偏斜反向时方向翻转 | `flips direction when the book turns short-heavy` |
| **逐块**（与块数成正比） | `advances the index in proportion to the number of blocks elapsed` |
| 同块幂等 | `is idempotent within a single block` |
| 首次触碰不追溯创世块 | `does not accrue from the genesis block on a feed's first touch` |
| **仅凭资金费即可清算** | `can push a position through its maintenance margin on its own` |
| 速率上限生效 | `lets the owner retune the rate, and refuses one above the ceiling` |
| 权限 | `refuses a rate change from anyone but the owner` |
| 无许可累积 | `lets anyone accrue funding, not just the owner` |

**受影响的既有测试**（已同批修改，均为「让资金费中性化」而非改判定）：

| 测试 | 改动 |
| --- | --- |
| `Is liquidatable exactly at the computed liquidation price` | 先开等额空单压平偏斜 |
| `Is not liquidatable one wei above the liquidation price` | 同上 |
| `Refuses to liquidate a healthy position` | 同上 |
| `Pays a winning long out of the pool` | 用**另一个账户**的等额空单对冲（不污染交易者余额） |
| `Leaves a losing long's remainder in the pool` | 同上 |

理由写在测试注释里：这些用例断言的是**PnL 与赔付算术**，若资金费同时生效，
它们会变成"顺便测资金费"，且 ±1 wei 的边界断言会失去意义。
