# ADR-002：金库偿付模型 —— 采用出金上限（Payout Cap）而非无界浮盈

- **状态**：已决定 —— 采用 **每笔头寸出金上限 + 精确储备累加器**
- **日期**：2026-10-07
- **触发**：
  - `docs/planning/缺陷分析-审计报告.md` GAP-01（付款失败致头寸永久卡死）、GAP-03（LP 抽干池子致盈利交易者被拒付）、GAP-04（`maxPnlCap` 设计已落文档、代码零实现）
  - `docs/推进方案.md:53`「设 `maxPnlCap`，池子付不出时明确 revert，绝不能凭空结算」
  - `docs/执行方案-后端与合约.md:215`、`:373` 同源要求
- **影响范围**：`contracts/contracts/perp/`（`PositionManager.sol` / `IPositionManager.sol` / `IVault.sol` / `PerpConstants.sol`）

---

## 1. 决策

**在开仓时为每笔头寸冻结一个「最大应付额」`payoutCapUsd`，储备取所有未平仓头寸的 `payoutCapUsd` 之和；平仓/清算时实际付款不得超过该上限。**

三个具体规定：

1. **上限构成**：`payoutCapUsd = collateralUsd + sizeUsd × MAX_PROFIT_BPS / BPS_DENOMINATOR`
   `MAX_PROFIT_BPS = 10_000`（即利润封顶为名义本金的 100%）。
2. **开仓准入**：`openPosition` 必须验证
   `totalAssets_after ≥ Σ payoutCapUsd_after`，否则 `revert InsufficientPoolCapacity()`。
   不满足即拒绝开仓——**宁可开不出来，不可开出来付不出**。
3. **储备口径**：`reservedAssets()` 返回 `totalPayoutCapUsd`（O(1) 累加器，非遍历）。

---

## 2. 背景：为什么必须改

缺陷分析已实测复现三条互相纠缠的失效（探针输出见 `缺陷分析-审计报告.md` §4.1）：

| 实测 | 现象 |
| --- | --- |
| PROBE-B | 池子付不出时 `Vault.payOut` revert（选择器 `0xa17e11d5` = `InsufficientLiquidity`），`_close` 已执行又被整笔回滚 → **头寸永久 `isOpen = true`，无任何出口** |
| PROBE-C | 单笔卡死头寸使**整批 20 笔清算全部回滚** |
| PROBE-F | `reservedAssets()` 只算本金，LP 合法提走全部本金后池子只剩 999，**盈利 1198.8 USD 的交易者平仓被拒付** |
| PROBE2 | 1,000 USDC 池 + 50x 多头，价格仅 **+2.25%** 盈利平仓即不可支付；20 笔 50x 涨 25% 时 **17 可平 / 3 不可平** |

根因是同一个：**池子的义务上界没有被定义，也没有被约束**。`reservedAssets()` 返回本金是个下界（交易者亏损时义务小于本金），而池子真实义务是 `本金 + 浮盈`，浮盈无界。

---

## 3. 备选方案与被否理由

| 方案 | 做法 | 否掉的理由 |
| --- | --- | --- |
| **A. 维持现状 + 封顶（本决策）** | 开仓时冻结 `payoutCapUsd`，储备取和 | —（采用） |
| B. 遍历全部未平仓头寸算实时浮盈 | `reserved = Σ max(collateral_i, collateral_i + pnl_i)` | **链上不可行**：头寸数无上界，`reservedAssets()` 会被 `Vault.removeLiquidity` 调用，gas 不可控。且 `Violation`：`Vault` 每次 LP 提取都要 O(n) 读预言机 |
| C. 按名义敞口设固定比例缓冲 | `reserved = 本金 + 名义 × bufferBps` | **数值上不可用**。实测场景（20×1000 USDC @50x，名义 999,000）下，缓冲 50% = 499,500，而池子只有 21,000 → LP 一分钱取不出、新仓一笔开不出。比例是拍脑袋的，且**不保证正确**（缓冲不足时仍会 revert，只是概率变小） |
| D. 仅维护净敞口（多空相抵） | `reserved = 本金 + Σ_feeds max(0, 净多头名义)` | **更接近对但仍有洞**：净敞口乘上任意价格变动就无界（涨 200% 时义务翻倍）。且需要 per-feed 敞口表 + 可枚举 feed 列表，改动面更大。**可作为 A 的后续优化**：净敞口为 0 时可放宽 `MAX_PROFIT_BPS` |
| E. 不封顶，只让 `payOut` 失败 | 现状 | 即 GAP-01：失败会回滚状态，头寸卡死。**已被实测证明不可接受** |

---

## 4. 为什么方案 A 是对的

1. **它把"池子的最大义务"变成了一个可计算的有限数**。开仓那一刻就知道这笔头寸最多赔多少，储备因此是**精确值而非近似值**。
2. **它让 `payOut` 不再可能因余额不足而失败**。
   证明：`payOut` 收到 `usdcAmount = amount / scale`（截断），`Vault` 检查 `usdcToUsd(usdcAmount) ≤ totalAssets`。
   而 `usdcToUsd(usdcAmount) = usdcAmount × scale ≤ amount ≤ equity ≤ payoutCapUsd`，
   且 `Σ payoutCapUsd = reservedAssets() ≤ totalAssets`（由开仓准入维持为不变式）。
   故检查恒成立 → **GAP-01 的第二条触发路径消失**。
3. **它顺带修复 GAP-04**：`maxPnlCap` 正是原始设计文档 `docs/推进方案.md:53` 要求的东西。本决策不是新增需求，是**补上未实现的既定设计**。
4. **它是 O(1) 的**：一个 `uint256` 累加器，开仓 `+=`，平仓/清算 `-=`。
5. **它让"精确性"可被测试**：可以断言 `totalAssets >= reservedAssets()` 在任何操作序列后都成立（不变式测试）。

## 5. 代价（必须写清楚，不掩饰）

| 代价 | 说明 | 缓解 |
| --- | --- | --- |
| **交易者利润被封顶** | 盈利超过名义本金 100% 的部分不再支付 | 演示叙事上这是**特性**而非缺陷（"资金池偿付保护"）；`MAX_PROFIT_BPS` 是常量，可调 |
| **开仓被拒的概率上升** | 池子容量不足时新仓直接 revert | 这是**有意为之**（纪律："宁可开不出来，不可开出来付不出"）。演示需按头寸规模配足流动性——已写入 `docs/changes/` |
| **`reservedAssets` 语义变更** | 从"本金之和"变为"最大应付额之和"，数值显著变大 | 现有 2 个测试断言旧口径，**必须同批更新**并标注为语义变更 |
| **`Position` 结构新增字段** | 加了 `payoutCapUsd`，ABI 变化 | 本模块**尚未部署**（`deployed_addresses.json` 仅含身份合约），无迁移成本 |

## 6. 连带决策（同批实施）

1. **清算赏金基数改为抵押品**（GAP-05）。
   现状 `reward = equity × 5%`，而破产头寸 `equity == 0` → **赏金恒为 0**，激励方向是反的（越需要清算的头寸越没人清）。
   改为 `reward = collateralUsd × 5%`。理由：清算时池子已没收抵押品，从没收品里分一部分给清算者是**自融资**的；且已证明清算时恒有 `equity < collateralUsd`（`collateral ≥ size/50`，而 `equity ≤ size/100`），故新基数**严格更大**且恒大于 0。
   实测依据：20 笔 50x 在 −15% 全部清算成功但赏金为 0。

2. **`liquidate` 改为逐笔容错**（GAP-02）。
   对 `vault.payOut` 使用 `try/catch`，单笔赏金付款失败只跳过该笔并 `emit PositionRewardFailed`，**不中断整批**。理由：批量清算是路演核心，不能被一笔坏账拖垮。

3. **零付款跳过而非 revert**（GAP-01 第一条触发路径）。
   `equity` 截断后不足 1 USDC 单位（`equity / usdcToUsdScale == 0`）时跳过付款，而不是让 `Vault.payOut` revert。实测 PROBE-A：`equity = 56 wei USD` 时整笔回滚、头寸卡死。

---

## 7. 重新评估的触发条件

- 引入**逐块资金费率**后，若 funding 累积被计入 `payoutCapUsd`，需重新推导上限公式；
- 头寸数量出现明确的工程上界（如每 feed ≤ 256 笔），使方案 B 的遍历变得可行且 gas 可控；
- 需要支持无上限利润的产品形态（如"无限上行"卖点）——此时应改为**分层池 / 社会化损失**模型，而非放宽上限。

---

## 8. 验证方式

不变式（必须写成常驻测试）：

```
∀ 操作序列:  totalAssets() >= reservedAssets()
```

边界（`±1 wei` 与精确相等，沿用既有风格）：

- 开仓恰好耗尽容量 → 成功；再多 1 wei → `InsufficientPoolCapacity`
- 盈利平仓：`pnl < cap` 时按实际付；`pnl > cap` 时付 `cap`（不是 revert）
- LP 提取到 `availableAssets()` 精确边界 → 成功；再多 → `InsufficientLiquidity`
- LP 提尽后交易者仍能按上限全额平仓（这一条直接证伪 PROBE-F）
- 破产头寸清算赏金 `> 0`
- 批量含一笔不可付款项 → 其余全部成交

实测输出见 `docs/planning/缺陷分析-审计报告.md` §4.1 与提交后的 `contracts/test/perp/SolvencyGuards.ts`。
