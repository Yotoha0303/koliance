## 1. 决策（四条）

### D1 · RFC-001 降格为「输入材料」，不是待实现的规格

RFC-001 自称 `[RFC-001]`，但**从未落进 `docs/adr/`**，也**从未有过配套实现计划**。
它是一份**外部输入的架构愿景**，价值在于两个技术原语，不在于它的 P0→P2 排期与目录树。

**结论**：RFC-001 **不照搬**。其中可复用的只有三处，逐条如下：

| RFC 章节 | 处置 | 理由 |
| --- | --- | --- |
| §4.2.2 PostgreSQL 双重记账 DDL | ✅ **可直接用** | RFC 里真正新增且高质量的部分（`settlement_ledger` 表） |
| §3.4 "Pluggable Policy Validator" 抽象 | ✅ **只留接口** | 纯叙事，一个空接口即可支撑赛道表述 |
| §4.2.1 两段 Lua 脚本（Redis 预扣） | ❌ **不采纳** | 4 个实测缺陷（GAP-18~21），见 §3 |
| §4.1.2 gRPC/proto 契约 | ❌ **不采纳** | 后端传输层是 `net/http`；`ADR-001` 明确不引入框架栈 |
| §4.3.1 CMake/Docker 目录结构 | ❌ **不采纳** | 与仓库分层冲突；且本仓无容器化（见 §4） |

### D2 · 不采用 Redis / gRPC / Docker（本次）

`10,000 TPS` 是 RFC 的目标，但**6 天内没有任何评委能验证 TPS**；
而"链上有个能逐块更新资金费率的合约"是当场能看的。

额度预扣若确需，**先用已有 PG 事务**（`SELECT ... FOR UPDATE`）——语义正确、可复现、零新增基础设施。
Redis 留作 **GAP-30**（赛后有余力再说，且**必须先修 GAP-18~21**）。

> 这与 `ADR-001`（不引入 Web 框架）同源：**新增基础设施必须换来可验证的价值**，否则不加。

### D3 · 不建第二套委托系统，复用 `agentcard`

RFC 把"从零建委托系统"当前提，但 `backend/internal/agentcard` **已有约 70% 的 P0**
（限额 / 日限 / 白名单 / 冻结 / 批次归集）。RFC **完全未引用它**。

**结论**：`agentcard` 是既有资产，**升级它**（补 EIP-712 验签），而不是并排再建一套。
这同时消掉 GAP-24（三套 Session Key 模型冲突）的**新增**风险。

### D4 · 项目范围 = 六环；04 构建环不处理也不标记

按 `想法记录.md` #4「只完成立项、需求、设计、开发、测试和发布，不做运维、故障和迭代」：

- **做**：立项 → 需求 → 设计 → 开发 → 测试 → 发布
- **不做**：运维 / 故障 / 迭代 / 自动化（**交平台处理**）
- **04 构建环**：本仓无 Dockerfile、无 `REVISION` 断言，**不处理、不标记、不阻断**
  （人工决定；理由与影响见 `docs/changes/010`）

## 2. 项目主题：双线程叙事

`docs/planning/项目目标.md` 只写了 perp（对标 GMX v1 单池），**完全未提 Agent 身份与委托**——
与 `想法记录.md` #1 脱节。收敛后主题明确为**两条线程 + 一条连接**：

| 线程 | 来源 | 交付物 | 状态 |
| --- | --- | --- | --- |
| **A · 链上可验证的永续** | `项目目标.md` | `Vault.sol` / `PositionManager.sol` / 逐块资金费率（ADR-003）/ 清算 Bot | 合约与 funding 已实现，**未部署** |
| **B · Agent 信任与身份** | `想法记录.md` #1、#3 | `agentcard` 委托限额 → **升级为 EIP-712** + `SessionKeyRegistry.sol` | 已有 70%，未升级 |
| **连接** | — | **自治 Agent 用 Session Key 在链上交易**——A 提供可交易的机制，B 提供"谁能交易"的授权 | 待做 |

**为什么这个组合成立**：RFC 想解决"Agent 如何自治执行"，但它把答案放在**链下**
（本地 Redis），评委看不见。改为：**授权走 B、执行落在 A 的链上合约**，
每一步都产生 tx hash —— 满足 `前沿资讯与竞品分析.md` 的评判口径
（"Judges need to be able to verify what you built"）。

### 待定项（`想法记录.md` #2，**不阻塞**）

> 评委更看重**可运行的 agent 交互协议**，还是 **Steam 证明的 ZK/信用模型**？

**本 ADR 不裁决此项**。当前默认按"**核心功能展示优先，数据采用模拟数据优先**"（#3）
推进双线程闭环；待有明确赛道口径后再定向。**不以未决问题阻塞开发。**

## 3. 为什么不采纳 RFC 的 Redis 方案（实测依据）

RFC §4.2.1 的两段 Lua 脚本有 **4 个已实测复现的缺陷**，详见
`docs/planning/推荐方案-自治Agent清结算.md` §2 与 `docs/GAP台账.md`：

| 编号 | 缺陷 | 后果 |
| --- | --- | --- |
| GAP-18 | `reserve` 无幂等键校验 | 同 `intent_id` 重复预扣 → **资金永久卡死** |
| GAP-19 | 冻结 TTL 过期后无回收路径 | 挂起的订单资金**永久卡死** |
| GAP-20 | `HINCRBYFLOAT` 浮点账本 | 实测漂移 **5e-12**（1000×0.001 ≠ 1） |
| GAP-21 | `daily_spent` 无重置机制 | 日限一旦触顶**永不恢复** |

**这四条不激活**（因为不采纳 Redis）。**若将来采纳，必须先修**——
修正规格见 `推荐方案` §3.4 的 F-01~F-06。

## 4. 后果

### 正面
- **主题不再漂移**：RFC 是"输入"，`项目目标.md` + 本 ADR 是"决定"，三级关系清晰。
- 消除了 RFC 与本仓库 **4 处结构性冲突**（GAP-22~25）的悬置状态——现在有裁决了。
- 保住了演示的可验证性：所有产出都落在链上或有 tx hash。

### 负面 / 代价
- **放弃 10,000 TPS 的性能叙事**。若评委明确看重吞吐量，这是本次最大的叙事损失。
  缓解：PG 事务方案语义正确，性能问题留到 GAP-25 用基准测试量化后再谈。
- **RFC 的 C4 图与 DDL 大部分不再被引用**，文档冗余度上升。
  缓解：RFC 保留为输入材料（不删，它记录了为什么被否决），由本 ADR 标注其地位。

### 遗留
- GAP-25（`agentcard` 全局锁 vs 高并发目标）**保留但不阻塞**——需先写基准测试量化，再见真章。
- GAP-30（Redis 额度池）维持 ⬜。
