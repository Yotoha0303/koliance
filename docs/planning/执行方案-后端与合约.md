原文判断"NVDA/TSLA 这类 equity feed 只在美股盘中更新，收盘后价格会冻住"，因此必须靠 `DemoOracle` 兜底。

**我一度根据 Pyth Hermes 的元数据认为 24/7 的 `Equity.Index.*` 能解决问题。这个结论是错的** —— 2026-10-06 用 `cast call` 直连 Monad 实测：

```

priceFeedExists(Equity.Index.NVDA/USD)      -> false     ← 未部署到 Monad
priceFeedExists(Equity.Index.TSLA/USD)      -> false     ← 未部署到 Monad
priceFeedExists(Equity.US.NVDA/USD)         -> true
```

**`Equity.Index.*` 在 Hermes 元数据里存在，但 Pyth 没有把它部署到 Monad 合约。** Monad 上只有盘中版 `Equity.US.*`，而它是**死的**：

```
getPriceUnsafe(Equity.US.NVDA/USD) -> price=22511000, expo=-5, publishTime=1778875218
当前时间                            -> 1791274890
                                      = 143.5 天前
```

不是"夜间冻住"，是**约 5 个月没人向 Monad 推送过美股更新**。拉取式预言机只在有人提交更新时才更新，测试网上没人提交。

**第二个问题：Hermes 的价格更新接口需要鉴权。**

```
GET /v2/price_feeds?...           -> 200  (元数据开放，所以我第一版方案被误导了)
GET /v2/updates/price/latest?...  -> 401  (需要 API key)
benchmarks.pyth.network           -> 404
```

**结论：演示所需的价格源必须是自己可控的，也就是 `DemoOracle`。** 加密 feed（BTC/ETH）走 Pyth 端到端可用；**美股 feed 在这条测试网上不可用**。

> ⚠️ 这是一次**以元数据代替链上实况**导致误判的教训：Hermes 的 feed 列表只说明 Pyth *有*这个 feed，不说明它*部署到了目标链*。判断可用性必须查目标链上的 `priceFeedExists`。

## 3. 阶段 1（2–3 天）：合约

目录：`contracts/contracts/perp/`。**不改 `Koliance.sol`**（身份合约与本次目标正交）。

### 3.1 `DemoOracle.sol`（先做，测试全靠它）

```solidity
contract DemoOracle is IPriceOracle {
    mapping(bytes32 => uint256) public prices;
    function setPrice(bytes32 feedId, uint256 price) external onlyOwner;
    function getPrice(bytes32 feedId) external view returns (uint256, uint256);
}
```
带 `bumpPrice(feedId, bps)` 便于前端一键"打跌 15%"。

### 3.2 `PythOracleAdapter.sol`

```solidity
contract PythOracleAdapter is IPriceOracle {
    IPyth public immutable pyth;  // 0x2880aB155794e7179c9eE2e38200202908C17B43

    function getPrice(bytes32 feedId) external view returns (uint256, uint256) {
        PythStructs.Price memory p = pyth.getPriceNoOlderThan(feedId, MAX_AGE);
        return (_normalize(p), p.publishTime);
    }
    // Pyth: int64 price + int32 expo(通常 -8) → 18 decimals
    function _normalize(PythStructs.Price memory p) internal pure returns (uint256) { ... }
}
```

**注意点**：
- Pyth 是 `int64 price` + `expo`，NVDA $180 存的是 `18000000000, expo=-8`。归一化到 18 decimals 时**先处理负指数再乘**，不要先乘后除（精度损失）。
- `expo` 必须从返回值读，**不要硬编码 -8**。
- 业务合约不直接调 Pyth，只调 `IPriceOracle`。

### 3.3 `Vault.sol`

- `addLiquidity` / `removeLiquidity`，LP 份额记账
- `totalAssets()` = USDC 余额
- **偿付能力护栏**：`maxPnlCap`，池子付不出时明确 revert，绝不凭空结算
- `payOut` / `receiveFees` 仅 `PositionManager` 可调（`onlyPositionManager`）

### 3.4 `PositionManager.sol`

```solidity
struct Position {
    address owner;
    bytes32 feedId;
    uint256 collateralUsd;   // 18 dec
    uint256 sizeUsd;         // collateralUsd * leverageBps / 1e4
    uint256 entryPrice;      // 18 dec
    bool    isLong;
    uint256 openedAt;
}
```

- `openPosition` / `closePosition` —— 开平各 0.1%，从 collateral 扣，进 Vault
- `pnl = sizeUsd * (exitPrice - entryPrice) / entryPrice`，空头取反
- 清算条件：`collateralUsd + pnl <= sizeUsd * MAINTENANCE_MARGIN_BPS / 1e4`
- 清算赏金：`LIQUIDATOR_REWARD_BPS`(5%) 给调用者

**批量清算的关键约束**（原方案只说"必须支持批量"，这里补上真正的难点）：

```solidity
function liquidate(uint256[] calldata positionIds, bytes[] calldata pythUpdateData) external
```

- 同一次调用内**所有头寸必须共用同一价格快照** —— 否则先清算的改变了状态，后面的判定基准就漂了。实现上：进入循环前，按 `feedId` 去重后统一 `getPrice`，缓存到内存，循环内只读缓存。
- 20 笔头寸可能跨多个 feed → **需要按 feed 去重 pythUpdateData**，不能 20 个仓位传 20 份同 feed 的更新（浪费 gas，且 `updatePriceFeeds` 会重复计费）。
- 建议结构：`feedId[] → 缓存价格` 的局部 map，先扫一遍收集用到的 feed，再逐个更新+读取，最后统一循环清算。

### 3.5 测试（`contracts/test/perp/`）

沿用现有 Hardhat 3 + viem + `node:test` 风格（见 `contracts/test/Koliance.ts`）。必测：

- 杠杆边界：1x / 50x 通过，50.01x revert
- 平仓盈利：池子付得出，LP 余额随之下降
- 清算阈值：恰好在阈值上 / 下 1 wei 的行为
- **池子偿付能力**：极端价格下单笔 PnL 超过池子余额 → revert 或封顶
- **批量清算**：一次传 20 笔，**含"其中几笔不该被清算"的混合情况**
- **`_normalize` 精度**：用真实 Pyth 返回值（expo=-8）验证，不要只用构造值

### 验收
`npx hardhat test` 全绿 + `scripts/demo-seed.ts`：注入流动性 → 一次性开 20 笔混合方向仓位。

### 4.2 `internal/oracle`：Hermes 客户端

**关键技巧**：Hermes 的 `/v2/updates/price/latest` 一次返回两样东西 —— `parsed`（给你算保证金率）和 `binary.data`（base64，直接喂 `updatePriceFeeds`）。**一个请求同时拿到触发信号和交易 payload**，不需要二次拉取。

```bash
GET https://hermes.pyth.network/v2/updates/price/latest?ids[]=<feedId>&encoding=hex
```

- 轮询间隔 ~100–200ms 即可。**不要用 SSE 流** —— 清算需要的是"最新快照"，轮询更简单且不会积压。
- 保留原始 `binary.data`，别解析后丢弃。

### 4.3 `internal/chain`：合约绑定

用 `abigen` 从 Hardhat 编译产物生成。注意 Hardhat 3 的 artifacts 路径与 v2 不同，确认 ABI JSON 位置后再生成，生成物提交进仓库（Render 构建时不应依赖 Hardhat）。

### 4.4 `internal/position`：头寸表

- 启动时 `eth_getLogs` 回填 `PositionOpened` / `PositionClosed` / `PositionLiquidated`
- WebSocket 订阅新区块增量更新
- **分块回填**：Monad RPC 对 `getLogs` 的区块跨度有限制，按 1000 区块切分并处理限流重试

### 4.5 `cmd/liquidator`：并发清算

**这是最容易翻车的地方，原方案已标注，这里给出具体做法。**

**本地 nonce 管理器（死保项）**
```go
type NonceManager struct {
    mu     sync.Mutex
    next   uint64
    chain  *ethclient.Client
    addr   common.Address
}
// 单 goroutine 持有，channel 发放；绝不用 PendingNonceAt 逐笔取
```
高并发下 `PendingNonceAt` 必然返回相同的值 → 交易互相覆盖 → 演示死在这里。

**Worker pool**
- 16–32 goroutine
- 待清算头寸**按同一价格快照分桶**，同桶打包成一次 `liquidate([]ids, [updates])`
- 打包前按 `feedId` 去重 update data

**Gas**
测试网直接拉高 `gasPrice`，不做动态估价。Monad 测试网 gas 便宜，不值得为省 gas 引入不确定性。

**冷启动**
Bot 启动时先做一次全量扫描，避免演示时"前 30 秒没反应"。

### 4.6 `cmd/api`：暴露清算事件

```
GET /api/v1/liquidations   → 最近清算列表（内存环形缓冲，最近 100 条）
```

前端大屏滚动展示用。**不要动现有 17 个路由**，新增即可（路由重构见 `ADR-001`，与本模块解耦）。

### 验收
前端点"价格下跌"后，Bot 日志 1 秒内出现 N 笔成功回执，Monad 浏览器能看到同区块 / 相邻区块的多笔清算交易。
