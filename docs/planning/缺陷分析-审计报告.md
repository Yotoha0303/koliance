## 3. 【可落地代码 / 配置 / 文档】缺陷清单

编号规则遵循 `提示词.md` 纪律 §4：**GAP-（质量缺口）**。严重度按"是否使演示失败 / 是否造成资金不可回收"排序。

### 3.1 严重（P0，资金卡死或经济性错误）

#### GAP-01 平仓与清算是"全或无"，付款失败即整笔回滚，头寸永久卡死 ✅ 实测

**位置**：`contracts/contracts/perp/PositionManager.sol:207-211`（closePath）、`:273-277`（liquidate 路径）；`contracts/contracts/perp/Vault.sol:165-181`（`payOut` 的三处 revert）

**机制**：`closePosition` 先 `_close(...)` 清零头寸状态，再无条件调 `vault.payOut(...)`。`Vault.payOut` 在三处会 revert：

```solidity
// Vault.sol:167-170
if (amount == 0) revert ZeroAmount();
uint256 usdcAmount = usdToUsdc(amount);   // 18 位 USD -> 6 位 USDC，截断
if (usdcAmount == 0) revert ZeroAmount(); // ← 截断到 0 即整笔回滚（实测触发器之一）
// Vault.sol:174-177
if (usdcToUsd(usdcAmount) > balanceUsd) revert InsufficientLiquidity(...); // ← 池子付不出即回滚
```

Solidity 的 revert 会回滚**整笔交易**，所以 `_close` 的效果一并撤销：头寸保持 `isOpen = true`，`openCollateralUsd` 继续占用 LP 储备，**且合约没有任何替代退出路径**（无 owner 强制平仓、无部分结算、无头寸转让）。后果是保证金永久锁死。

**实测到的两个触发路径**：

| 触发路径 | 探针 | 实测输入 | 实测结果 |
| --- | --- | --- | --- |
| 权益舍入到 0 USDC | PROBE-A | DemoOracle 价格设为 `162000000000000000001`（即 162 + 1 wei） | `liquidatable=true`、`equity=56` wei USD，`closePosition` revert，`isOpen` 仍为 true ✅ |
| 池子付不出 | PROBE-B | 50x 多单，价格 180 → 3600（+1900%） | `closePosition` revert，错误选择器 `0xa17e11d5` = **`InsufficientLiquidity(uint256,uint256)`**（已用 `toFunctionSelector` 反查命名，见 PROBE-E），`isOpen` 仍为 true，交易者余额 `0` ✅ |

**影响**：
1. 受影响的头寸**无法以任何方式平掉**，保证金不可回收；
2. `reservedAssets()` 永久包含这笔死头寸 → LP 的 `availableAssets` 被永久压低（`Vault.sol:143-145`）；
3. 演示层面：一旦发生，大屏上会出现"点了平仓没反应"的头寸，且没有补救按钮。

**诚实限定（不可夸大）**：舍入窗口（`equity ∈ (0, 1e-6 USD)`，对应价格相对宽度约 **1e-10**）在连续预言机下极难命中，属**潜在正确性缺陷**而非高频故障；**池子付不出**路径才是现实可达的那条（阈值见 GAP-04）。

#### GAP-02 单笔卡死头寸污染整批清算 ✅ 实测

**位置**：`PositionManager.sol:221-281`（`liquidate` 无 per-position 容错）

**机制**：`liquidate` 在一个循环内对每笔待清算头寸调 `vault.payOut(msg.sender, reward)`。任意一笔的 `payOut` revert，**整批 20 笔全部回滚**——包括那些本来完全健康、可以正常清算的头寸。

这与 `IPositionManager.sol:56-62` 冻结契约里写的「所有头寸必须共用同一价格快照」是两件事：快照保证了**判定一致性**，但没有保证**执行原子性的边界**。契约注释只解决了前者。

**实测（PROBE-C）**：
```
PROBE-C pos1 liquidatable=true
PROBE-C pos2 liquidatable=true      ← 两笔都是"可清算"
PROBE-C batch liquidate reverted=true
PROBE-C pos1 still open=true        ← 整批回滚
PROBE-C pos2 still open=true
```
构造方式：两笔 10x 多单（保证金各 999 USD），价格设为 `162e18 + 1`。此时两笔权益都落在 GAP-01 的舍入窗口内，各自单独清算都会 revert，合并成批仍然整体 revert。

**影响**：这是路演核心（`docs/项目目标.md:22-23` 要求"数十笔头寸的链上自动清算"）的**致命路径**。Go Bot 只要把一笔不可付款的头寸和健康头寸打进同一个 `liquidate([])` 调用，那一次批量清算**全部失败**，而 Bot 日志会显示"批量清算失败"，从链上完全看不出是哪一笔的问题——**排障信息在 revert 时被丢弃了**。

#### GAP-03 `reservedAssets` 只算本金、不算浮盈 → LP 可抽走本金，盈利交易者拿不到钱 ✅ 实测

**位置**：`PositionManager.sol:298-304`、`Vault.sol:196-199`、`Vault.sol:143-145`

**机制**：`reservedAssets()` 返回 `openCollateralUsd`——**只统计开仓本金**。但池子的真实义务是 `collateral + 浮盈`（亏损时义务更小，所以本金是"上界"这个说法只在**交易者亏损**时成立）。`Vault.removeLiquidity` 用 `availableAssets = totalAssets - reserved` 作为 LP 的提取上限，于是：

- 当某个头寸**浮盈超过自身本金**时，`totalAssets()` 里**包含**这笔尚未实现的盈利（它就是池子里的钱），`reserved` 却**不包含**这笔盈利；
- LP 可以合法地把自己那部分本金全部提走，只留下 `reserved`；
- 此时盈利交易者来平仓 → `payOut` 超出余额 → revert → 触发 **GAP-01 的头寸卡死**。

**实测（PROBE-F）**，这是本次审计最具决定性的一条：
```
totalAssets=2000                    ← LP 投入 1000 + 交易者保证金 1000
reservedAssets=999                  ← 只算本金
availableAssets=1001                ← LP 被允许提走 1001
at +12%: unrealizedPnl=1198.8 USD   ← 交易者真实浮盈
obligated (collateral+pnl)=2197.8 USD  ← 池子真实义务
LP max burnable shares=500500000000000000000 of 1000000000000000000000
LP withdrew=20001 USDC              ← LP 拿回 20000 本金 + 1 手续费（!!）
pool totalAssets now=999
trader closePosition succeeds=false     ← 盈利交易者被拒付
trader still open=true                  ← 头寸卡死
```
> 注意 `LP withdrew=20001 USDC`：LP 投的是 20,000、份额占一半，但本金**全额**拿回（因为开仓手续费 1,000×0.1%×20 = 20 USD 沉淀进了池子）。这不是 bug，但说明演示资金流是"LP 稳赚手续费"结构，亏损兜底方只有交易者。

**影响**：LP 的第一优先级（本金可退出）被满足，代价是把**盈利交易者的应收款**变成了不确定项。这在 `Vault.sol:25-27` 的注释里被描述为已解决（"A pool that cannot pay must revert, never settle a shortfall by minting value"）——revert 确实没有凭空造钱，但**它把损失转嫁给了交易者，而不是按 LP 份额分摊**。设计意图（`docs/推进方案.md:53`「池子付不出时明确 revert，绝不能凭空结算」）被字面满足，但经济后果未在文档中量化。

#### GAP-04 `maxPnlCap` 设计已落文档、代码零实现；开仓侧无偿付护栏 ✅ 阈值实测 / 实现缺失实读

**位置**：设计要求见 `docs/推进方案.md:53`、`docs/执行方案-后端与合约.md:215`、`:373`；代码侧 `grep -r "maxPnlCap"` **全库零匹配** ✅

```

reserved=19980
```
即：LP 自有资金 **1,000 USD**，对开仓头寸的名义敞口 **20 × 49,950 = 999,000 USD**。

**「盈利平仓在什么价位变得不可支付」——实测阈值表**（用 `simulateContract` 逐步试探，池子规模为 LP 本金）：

| LP 池 | 杠杆 | 平仓变为不可支付的涨幅 |
| --- | --- | --- |
| 1,000 USDC | 1x | > +40%（未触发） |
| 1,000 USDC | 5x | **+20.25%** |
| 1,000 USDC | 50x | **+2.25%** |
| 10,000 USDC | 5x | > +40% |
| 10,000 USDC | 50x | **+20.25%** |

### 3.2 高（P1，设计正确性）

#### GAP-05 清算赏金在破产头寸上归零 → 理性 Bot 不会清算坏账 ✅ 实测

**位置**：`PositionManager.sol:270-277`（`reward = equity * LIQUIDATOR_REWARD_BPS / BPS`）、`PerpConstants.sol:33`（`LIQUIDATOR_REWARD_BPS = 500`）

**机制**：`_equityAfter`（`:357-361`）把权益下限截断到 0。破产头寸（亏损 ≥ 本金）权益恰为 0 → `reward = 0` → `if (reward > 0)` 为假 → **不给清算者任何报酬**，但**头寸照样被关闭**。

**实测**：PROBE2 的 20 笔 50x 场景，价格砸 **-15%**（180→153），所有 20 笔均已远超 50x 的清算线（-2%），权益全部截断为 0：
```
after -15%: liquidate ok=3 reverted=0
```
调用成功、无 revert、无付款——即**赏金为 0**。这与"清算赏金是 Bot 的经济动机"这个前提直接冲突。

**对照**：在**恰好**触及清算线时赏金是良性的：实测 `equity = size × 1%`，赏金 = 其 5%——1x 为 0.4995 USDC、10x 为 4.995 USDC、20x 为 9.99 USDC。所以**不是"赏金总是太小"，而是"越接近破产、赏金越趋近 0，而越破产越需要被清算"**——激励方向是反的。

**影响**：Go 清算 Bot（尚未编写）若按正常经济逻辑设计，会跳过所有坏账头寸。演示中"数十笔清算"能成立，仅因为**演示者会在前端手动按下按钮**（`DemoControlPanel` 的"一键清算"），而不是因为激励成立。这一点在 `docs/推进方案.md` 与 `docs/执行方案-后端与合约.md` 中均未被指出。

#### GAP-07 `closePosition` 无价格时效/滑点约束 📖

**位置**：`PositionManager.sol:185-191`

**实读**：`closePosition` 调 `oracle.getPrice(p.feedId)` 后**直接采用返回值**作为 `exitPrice`，没有 `minOut` / `maxSlippage` / `deadline` 之类的调用者参数。`IPositionOracle` 也不暴露 `publishTime` 供业务层做时效判定——虽然 `getPrice` **返回**了 `publishTime`，但 `PositionManager.sol:148` 与 `:191` 都用 `(uint256 price, )` 把它丢弃了。

**影响**：演示路径下，调用者无法约束成交价。对演示无害（演示者就是价格源），但**任何接真实资金的部署都不能沿用此路径**，而代码里没有任何地方写着这个限制。

#### GAP-08 `_pushPrices` 用字符串签名调用 + 静默吞掉失败 📖

**位置**：`PositionManager.sol:316-324`

```solidity
(bool ok, ) = priceUpdater.call(
    abi.encodeWithSignature("updatePriceFeeds(bytes[])", pythUpdateData)
```

**实读问题**：① `abi.encodeWithSignature` 用**裸字符串**拼选择器，签名一旦与 `PythOracleAdapter.updatePriceFeeds(bytes[])` 漂移，调用会**静默 miss**（选择器不匹配 → 打到不存在的函数 → 返回空但 `call` 本身成功或失败都被吞）；② `ok` 被显式丢弃且**不发事件**，链上没有任何痕迹说明这次推送失败了。

**已缓解的部分（必须承认）**：`contracts/test/perp/PositionManager.ts:550-597` 有一条测试**专门**验证该签名未漂移（"if that signature drifted from the adapter's, the call would silently miss and `updateCallCount` would stay zero"）✅ 这条测试是有效的护栏。缺口在于：**失败时无观测**（演示时若 Pyth 更新因余额不足全部失败，日志与链上均无信号），以及**未从接口取选择器**（`IPyth` 已在 `interfaces/IPyth.sol` 定义，本可直接 `IPyth(priceUpdater)`）。
