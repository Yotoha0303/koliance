# Koliance 阶段性推进方案

> 目标来源：`docs/项目目标.md`（GMX v1 式单池永续合约 Demo：Vault + PositionManager + Pyth 拉取式预言机 + Go 清算 Bot + 前端演示面板）

---

## 0. 现状盘点（结论先行）

目标要求的是一套永续合约系统，仓库现有的是链上身份/信任凭证系统。两者唯一重叠处是 Monad 部署链路和前端外壳。

| 目标要求 | 仓库现状 | 差距 |
| --- | --- | --- |
| `Vault.sol` 流动性金库 | 不存在 | 全新 |
| `PositionManager.sol` 开平仓 / 杠杆 | 不存在 | 全新 |
| Pyth 拉取式预言机 | 不存在 | 全新 |
| Go 清算 Bot | `backend/cmd/api/main.go:30` 仅返回硬编码 mock，不连链 | 新写，非"接入" |
| K 线 / 杠杆滑块 / 持仓列表 / 模拟清算面板 | `MarketTerminal.tsx` 只读行情 + RSI，无交易交互 | 增量开发 |
| Monad 测试网部署 | 已跑通：`Koliance` @ `0x32fDd6B0...`，chain 10143 | **直接复用** |

**结论：不要改 `Koliance.sol`。** 身份合约与本次目标正交，作为独立叙事模块保留（演示时一句话带过）。新增独立的 `contracts/contracts/perp/` 目录，前端复用 `Navbar` / `CursorTrail` / `MarketTerminal`。这样既保住已有的 demo 资产，也避免把可运行的东西改坏。

### 三个需要先拍板的决策

1. **抵押资产**：先确认 Monad 测试网是否有官方 USDC；**没有就自带 `MockUSDC`（6 decimals）用 Ignition 部署**，不要等水龙头、不要把演示卡在外部依赖上。
2. **Pyth 美股喂价的空窗期**：NVDA/TSLA 这类 equity feed 只在美股盘中更新，收盘后价格会冻住，demo 会"点了没反应"。因此**必须做价格注入口**（见阶段 1 的 `DemoOracle`），把 Pyth 定位成"生产路径"，演示走可控路径。
3. **TradingView 是否强需求**：它是本方案里性价比最低的一环（引入外部依赖、深色 UI 难统一）。建议用现有折线图替代，把省下的时间投到清算演示的稳定性上。若坚持要 K 线，用 `lightweight-charts` 自绘，不要用 embedded iframe widget。

## 阶段 0（0.5 天）：定桩与接口冻结

这一阶段的目的只有一个：让前后端和合约能并行开工，互不阻塞。

- 新建 `contracts/contracts/perp/`，冻结三个接口：
  - `IPriceOracle`：`getPrice(bytes32 feedId) returns (uint256 price, uint256 publishTime)`
  - `IVault`：`addLiquidity` / `removeLiquidity` / `totalAssets`
  - `IPositionManager`：开仓 / 平仓 / `liquidate`
- **`IPriceOracle` 的抽象是全局关键**：业务合约只依赖接口，生产实现走 `PythOracleAdapter`，演示实现走 `DemoOracle`。后续替换不动任何业务代码。
- 确认 Pyth 在 Monad 测试网的合约地址（从 [Pyth 官方文档](https://docs.pyth.network/)核对，**不要照抄其他链的地址**），写入 `contracts/.env` 与根目录 `.env.local`。
- 部署 `MockUSDC` + `DemoOracle` 到 Monad 测试网。
- 冻结一份共享常量：`contracts/lib/perpConfig.ts`（`openFeeBps` / `maintenanceMarginBps` / `liquidatorRewardBps` / feedId 表），前端 `src/lib/perp.ts` 直接 re-export 它。

**验收**：`npx hardhat ignition deploy ignition/modules/DemoOracle.ts --network monadTestnet` 成功，Monad 浏览器上能看到地址。

## 阶段 1（2–3 天）：合约与预言机

### 1.1 `Vault.sol` — 流动性金库

- `addLiquidity(uint256 amount)` / `removeLiquidity(uint256 shares)`，LP 份额记账
- `totalAssets()` = USDC 余额；手续费累积进池（`collectFees()`）
- 偿付能力护栏：设 `maxPnlCap`，池子付不出时明确 revert，**绝不能凭空结算**

### 1.2 `PositionManager.sol` — 开平仓与清算

```solidity
struct Position {
    address owner;
    bytes32 feedId;
    uint256 collateralUsd;
    uint256 sizeUsd;      // collateralUsd * leverageBps / 1e4
    uint256 entryPrice;
    bool    isLong;
    uint256 openedAt;
}
```

- `openPosition(bytes32 feedId, uint256 collateralAmount, uint256 leverageBps, bool isLong, bytes[] pythUpdateData)`
- `closePosition(uint256 positionId, bytes[] pythUpdateData)`
- 手续费：开/平各 0.1%（`openFeeBps = 10`），从 collateral 直接扣，进 Vault
- PnL：`pnl = sizeUsd * (exitPrice - entryPrice) / entryPrice`，空头取反
- 清算条件：`collateralUsd + pnl <= sizeUsd * maintenanceMarginBps / 1e4`（建议 `maintenanceMarginBps = 100`，即 1%）
- 清算赏金：从剩余 collateral 里划 `liquidatorRewardBps = 500`（5%）给调用者
- **`liquidate` 必须支持批量**：`liquidate(uint256[] positionIds, bytes[] pythUpdateData)`。这是路演高光（数十笔同区块清算）的技术前提，事后再改会牵动 Go Bot 的整条打包逻辑。

### 1.3 预言机接入

- `PythOracleAdapter.sol implements IPriceOracle`：内部持 Pyth 合约地址，走 `updatePriceFeeds` + `getPriceNoOlderThan`
- feedId（NVDA/USD、TSLA/USD、BTC/USD）从 Hermes 查出后落成常量表
- `DemoOracle.sol implements IPriceOracle`：`setPrice(feedId, price)` 仅 owner 可调 → **前端"模拟价格"面板直接调它，这就是 1 秒清算演示的开关**

### 1.4 测试（沿用现有 Hardhat + viem 风格）

必测边界，每条都是 Demo 会踩的坑：

- 杠杆边界：1x / 50x / 超上限应 revert
- 平仓盈利：池子付得出，LP 余额随之下降
- 清算阈值：恰好在阈值上 / 下 1 wei 的行为
- **池子偿付能力**：极端价格下单笔 PnL 超过池子余额 → 必须 revert 或有封顶
- 批量清算：一次传 20 笔，含"其中几笔不该被清算"的混合情况

**验收**：`npx hardhat test` 全绿 + 一个 `scripts/demo-seed.ts`：注入流动性 → 一次性开 20 笔混合方向仓位。

## 阶段 2（2 天）：Go 清算 Bot

现有 `main.go` 是纯 mock，本次是**新写一个 cmd**，不是改造。建议同仓多入口：

```
backend/
  cmd/api/          # 保留，转为给前端喂清算事件
  cmd/liquidator/   # 新增：清算 Bot
  internal/chain/   # go-ethereum 客户端 + abigen 生成的合约绑定
  internal/oracle/  # Pyth Hermes 价格流
  internal/position/# 头寸缓存与盈亏计算
```

**2.1 数据流**
- 启动时 `eth_getLogs` 回填 `PositionOpened` / `PositionClosed` → 内存头寸表
- WebSocket 订阅新区块（`wss://testnet-rpc.monad.xyz`）增量更新
- Pyth Hermes 实时价（`hermes.pyth.network`，SSE/WS）驱动扫描
- 每个价格 tick 扫描头寸表算保证金率

**2.2 并发清算（最容易翻车的地方）**
- Worker pool（16–32 goroutine），待清算头寸按**同一价格快照分桶**打包 —— 批量 `liquidate` 里所有仓位必须共用同一个价格快照
- **本地 nonce 管理器**：绝不能用 `PendingNonceAt` 逐笔取，高并发下必然 nonce 冲突，Demo 就会死在这里
- 测试网直接拉高 `gasPrice`，不做动态估价

**2.3 观测**
- 每笔清算打结构化日志 + `GET /api/v1/liquidations` 暴露最近清算列表 → 前端大屏滚动展示

**验收**：前端点"价格下跌"后，Bot 日志 1 秒内出现 N 笔成功回执，Monad 浏览器能看到同区块 / 相邻区块的多笔清算交易。

## 阶段 3（2–3 天）：前端与演示打磨

- **3.1 K 线**：`/api/market` 已返回真实 `chart.timestamps/closes`，直接喂给 `lightweight-charts`（若时间紧则砍掉，用现有折线）
- **3.2 `PositionPanel.tsx`**：开仓表单（标的 / 方向 / 保证金 / 杠杆滑块 1–50x / **实时预估强平价**）+ 持仓列表（未实现盈亏、保证金率进度条）
- **3.3 `DemoControlPanel.tsx`**（仅演示用）：`调低价格 -15%`（调 `DemoOracle.setPrice`）、`一键清算`、`重置演示状态`
- **3.4 强平价公式必须同源**：前端强平价与链上实际清算价不一致，是这类 Demo 最经典的翻车点。公式只写一份，放 `src/lib/perp.ts`，与 `contracts/lib/perpConfig.ts` 共享 bps 常量
- **3.5 彩排清单**（必须完整跑通一遍）：
  1. 冷启动 → 连钱包 → 自动切到 10143
  2. 存入 1000 USDC 流动性
  3. 脚本开 20 笔混合方向仓位
  4. 大屏点"调低价格" → < 1s 内持仓批量变红 → Bot 日志滚动 → 浏览器出块确认
  5. 全程 90 秒内走完，无手动补救

## 风险清单

| 风险 | 影响 | 对策 |

| Pyth 美股喂价仅盘中更新 | 夜间/周末 demo 价格不动 | `DemoOracle` 兜底，Pyth 作为"生产路径"讲 |
