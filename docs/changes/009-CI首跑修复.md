- **日期**：2026-10-07
- **环**：03 测试
- **类型**：缺陷修复（**仅真实 CI 可发现**）
- **关联**：GAP-10、GAP-32、GAP-35
- **分支**：`feat/perp-solvency-and-panel`
- **提交**：`1ac689a`、`e48ed61`、`f6ec42d`

> **为什么单独成篇**：这三个问题**本机全部是绿的**。
> 它们只有在 GitHub Actions 上跑一次才暴露，因此不属于任何既有变更记录的覆盖面。
> 补录于此，避免它们变成"改了就没人知道为什么"的历史。

## 问题 1：workflow 从未被触发（`1ac689a`）

### 现象

PR #5 打开后，`gh pr checks` **只显示 Vercel 一项，零 check-run**。
而 `gh api repos/Yotoha0303/koliance/contents/.github/workflows/ci.yml?ref=feat/...`
确认**文件在分支上、3634 字节、非空**。

### 排查过程

| 检查 | 结果 |
| --- | --- |
| workflow 文件是否在分支上 | ✅ 在 |
| fork 的 Actions 是否启用 | ✅ `{"enabled":true,"allowed_actions":"all"}` |
| 上游 Actions 权限 | ❌ `403`（token 缺 fine-grained 权限，**无法读取**） |
| head commit 的 check-runs | **空** |
| 上游 `main` 是否有 workflow | **无**（404） |

### 根因（两个叠加）

1. **触发条件写错**：`push: branches: [main]` —— 推的是 feature 分支，**不匹配**。
2. **fork 的 `pull_request` 运行有前置条件**：需要 base 仓库启用 Actions **且**
   workflow 已存在于 base 分支。上游 `main` 上没有 `ci.yml`，所以这条路径也不通。

### 为什么原写法对本项目是错的

本仓库的协作模式是**分支在 fork、PR 从 fork 来**（PR #3、#4 均如此）。
`branches: [main]` 意味着贡献者推自己的分支后**看不到任何结果**，
而维护者是第一个发现失败的人。

### 修复

`push: branches: ["**"]` —— 所有分支触发，绕开第 2 个前置条件。

**验证**：修复后推一次，`gh run list` 立刻出现 `in_progress` 的运行。

## 问题 2：`tsc` 跑在 `hardhat compile` 之前（`e48ed61`）

### 现象

CI 的 `contracts` job 在 Typecheck 步骤失败，**110 个类型错误**，
分布在**本分支完全没碰过**的文件里：

```
scripts/demo-seed.ts(132,14):   TS2345  'unknown' not assignable to 'bigint'
scripts/transfer-test.ts(45,9): TS18046 'tokenBal' is of type 'unknown'
test/Counter.ts(41,27):         TS2339  Property 'by' does not exist on type 'never'
test/KolToken.ts(44,15):        TS18046 'minerBalance' is of type 'unknown'
test/Koliance.ts(16,18):        TS18046 'identity' is of type 'unknown'
```

**同一条命令在本机 `exit=0`，零错误、零输出。**

### 排查过程

逐步排除，每步都有实测：

| 假设 | 检查 | 结论 |
| --- | --- | --- |
| 本地依赖版本不同 | 比对 `node_modules` 与 lockfile 的 typescript / viem / hardhat | **完全一致**（7.0.2 / 2.55.19 / 3.14.0） |
| 本地有陈旧构建缓存 | 删 `.next`、`coverage`、重跑 tsc | 仍然 exit=0 |
| 本地有未提交文件在遮掩 | **`git clone` 一份纯净树**重跑 | **复现 110 个错误** ✅ |

第三步定位到根因。

### 根因

**`artifacts/` 被 gitignore，而 Hardhat 的 viem 插件从它推导合约类型。**

- 纯净检出：无 `artifacts/` → 没有合约类型 → 每个 `viem.deployContract(...)`
  返回 `unknown` → 110 个错误；
- 我的工作树：跑过 `hardhat test` 无数次，`artifacts/` 早已生成 → 类型齐全 → 全绿。

**这就是「在我机器上能跑」，而且是 CI 自己的首次运行抓到的。**

### 修复

交换步骤顺序：**先 `hardhat compile`，再 `npx tsc --noEmit`**。

```yaml
- run: npm ci
- name: Compile contracts      # ← 先生成 artifacts/，即合约类型
  run: npx hardhat compile
- name: Typecheck              # ← 现在能看到类型了
  run: npx tsc --noEmit
```

`tsc` 这一步**仍然必要**：Hardhat 3 只编译 `.sol`，
测试 / 脚本 / ignition 模块里的跨模块类型错误它永远发现不了
（`2b05f05` 就靠它抓到 2 个上游遗留的类型错误）。

### 验证

在**纯净 clone** 上复跑，不是在工作树上：

```
无修复：110 errors
有修复：compile → tsc exit=0 → 146 passing → 覆盖率门禁通过
```

## 问题 3：覆盖率阈值按错误的行尾口径标定（`f6ec42d`）

### 现象

CI 的覆盖率门禁步骤失败：

```
DemoOracle.sol         lines  91.30%      （本机 94.29%）
PythOracleAdapter.sol  lines  77.50%      （本机 89.41%）
PositionManager.sol    lines  92.45%      （本机 96.54%）
Vault.sol              lines  81.67%      （本机 88.04%）
TOTAL                  lines  89.22%      （本机 94.37%）
✗ Coverage below floor: lines 89.22% < 93%
```

**同一份源码、同一个 solc（0.8.31，evm target osaka）、同一批 146 个通过的测试，
差 5 个百分点。** 而且**每个文件的"未覆盖行数"在 CI 上更多**。

### 排查过程

| 假设 | 检查 | 结论 |
| --- | --- | --- |
| 本地有陈旧 coverage 数据 | 删 `coverage/` 重跑 | 仍然 94.37% |
| solc 版本不同 | 比对两侧日志 | **完全相同**：`Compiled 20 Solidity files with solc 0.8.31 (evm target: osaka)` |
| 依赖版本不同 | 比对 lockfile 与安装 | 一致 |
| 本地工作树与 CI 的差异 | `git clone` 纯净树 | **复现 89.22%** ✅ |

然后对纯净树做**单项变量测试**：把 `*.sol` 强制转成 LF 后重跑 —— **仍是 89.22%**，
说明纯净树本身就是 LF，而我的工作树是 CRLF。

### 根因

**Hardhat 的覆盖率插桩按字节偏移（byte offset）把执行的字节码映射回源码。**

CRLF 与 LF 的"同一行"字节范围不同 → 插桩的可执行语句集合不同 → 测量结果不同。

- 我的 Windows 工作树：**CRLF** → 94.37%
- CI（Linux）：**LF** → 89.22%

**阈值 93% 是在本机 94.37% 之上定的 —— 定的是一个测量机器的产物，不是代码的属性。**
它从来没有反映过 CI 会看到的数。

### 修复（两件事）

1. **阈值改以 LF 为准**（CI 与所有 Linux 协作者看到的口径）：95% → **88%**，
   低于实测 89.22% 一个点，理由同 `007`：设在当前值会在下一次无关重构时失败然后被删。
2. **新增 `.gitattributes`**，把 `*.sol` / `*.ts` / `*.md` 等固定为 `eol=lf`，
   让 Windows 检出与 CI 一致。

脚本注释里写明：**任何覆盖率读数必须取自重新检出后的树**，
不要取长期存在的 Windows 工作树 —— **它会读到偏高约 5 个点的值**。

### ⚠️ 未做的部分（记为 GAP-35）

`.gitattributes` 只对**后续**检出生效；现有文件在工作树里仍是 CRLF。
让它们生效需要：

```bash
git add --renormalize . && git checkout -- .
```

**本次没有做**：它会在一个已经有 52 个文件的 PR 里混入成千上万行行尾噪声，
**使真正的改动无法评审**。留给独立的小 PR。

### 验证

在纯净 LF clone 上跑完整的 `contracts` job：

```
npm ci → added 163 packages
hardhat compile → Compiled 20 Solidity files
tsc --noEmit → exit=0
hardhat test --coverage → 146 passing
check-coverage.ts → 89.22% ≥ 88%  ✓ exit=0
```

## 三者的共性（值得单独记下）

| # | 表现 | 错误的环境假设 |
| --- | --- | --- |
| 1 | workflow 未触发 | 以为 `branches: [main]` 会覆盖 feature 分支；以为 fork 的 PR 一定会跑 CI |
| 2 | 110 个类型错误 | 以为检出必有 `artifacts/`（它被 gitignore） |
| 3 | 覆盖率差 5 个点 | 以为覆盖率是代码的属性，不知道它依赖行尾 |

**没有一个是逻辑想错。** 全部是**对工具/环境行为的不正确假设**，
而且**全部在本机不可见** —— 本机怎么跑都是绿的。

> 这正好回答了"CI 到底值不值"这个问题：**这一批里最有价值的三个发现，
> 只有 CI 能发现。** 靠本机自测永远抓不到。

同时也要诚实标注：`2b05f05` 的提交信息里写了
"workflow 本身未在 GitHub Actions 上跑过" —— **这个标注是准确的**，
问题确实就出在没跑过的那部分。**先标注再验证** 比假装验证过要好，
但它不能替代真的跑一次。
