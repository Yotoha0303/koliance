## 背景：一个悬置了很久的决策

`docs/GAP台账.md` §4 的四个条目（GAP-22~25）一直标着"**需要谁决策：架构**"：

| GAP | 冲突 |
| --- | --- |
| GAP-22 | RFC-001 把"从零建委托系统"当前提，但 `backend/internal/agentcard` 已有约 70% 的 P0 |
| GAP-23 | RFC 要求 Redis + gRPC + proto + Docker；仓库只有 `net/http` + pgx。且 RFC 内部 4 处自相矛盾 |
| GAP-24 | 三套 Session Key 模型互不兼容，无代码把内存态写入 PG |
| GAP-25 | `agentcard/service.go:95` 全程持全局锁 vs RFC 的 10,000 TPS 目标 |

同时 `docs/planning/项目目标.md` **只写 perp，完全未提 Agent 身份与委托**——
与 `想法记录.md` #1 明示的主题脱节。**RFC 是"输入"还是"规格"从未说清**，
导致规划文档里两种成熟度的叙述并存（违反纪律 D4）。

---

## 决策：`ADR-004`（四条）

**D1 · RFC-001 降格为输入材料。** 它自称 `[RFC-001]` 却从未落进 `docs/adr/`，
也从未有过配套实现计划。**只复用三处**：§4.2.2 的 `settlement_ledger` DDL、
§3.4 的 ZK Validator 空接口、§1.2 的 EIP-712 授权语义。其余不照搬。

**D2 · 不采纳 Redis / gRPC / Docker。** `10,000 TPS` 是 RFC 的目标，
但**6 天内没有评委能验证 TPS**；而"链上有个能逐块更新资金费率的合约"是当场能看的。
额度预扣若确需，先用已有 PG 事务。**这与 `ADR-001` 同源：新增基础设施必须换来可验证的价值。**

**D3 · 不做第二套委托系统。** `agentcard` 是既有资产（约 70% 的 P0 已在），
RFC 完全未引用它。**升级它**（补 EIP-712），而不是并排再建一套。

**D4 · 范围 = 六环；04 构建环不处理也不标记**（承接 `docs/changes/010` 的人工决定）。

### 主题收敛：双线程 + 一条连接

| 线程 | 交付物 | 状态 |
| --- | --- | --- |
| **A · 链上可验证的永续** | `Vault` / `PositionManager` / **逐块资金费率**(ADR-003) / Go 清算 Bot | 已实现，**未部署** |
| **B · Agent 信任与身份** | `agentcard` → **升级 EIP-712** + `SessionKeyRegistry.sol` | 已有 70%，**未升级** |
| **连接** | **自治 Agent 用 Session Key 在链上交易** | 待做 |

**为什么成立**：上游 RFC 想解决"Agent 如何自治执行"，但把答案放在**链下**（本地 Redis），
评委看不见。改为**授权走 B、执行落在 A 的链上合约**——每步都有 tx hash，
满足"Judges need to be able to verify what you built"（`前沿资讯与竞品分析.md`）。

### 未裁决项（`想法记录.md` #2，不阻塞）

> 评委更看重**可运行的 agent 交互协议**，还是 **Steam 证明的 ZK/信用模型**？

**ADR-004 明确不裁决此项**，当前按 #3「核心功能展示优先，模拟数据优先」推进双线程闭环。
**不以未决问题阻塞开发。**
