## 新增 1：`DemoControlPanel.tsx` —— 演示扳机

放在 `/perp` 页面右侧（与持仓同屏：价格滑块与清算是各一键，观众正看着这块屏）。

**直接读链，不经过 Go Bot**，这是刻意的选择而非省事：

- Bot 的接链部分正是 **GAP-26**，它没落地之前演示**根本跑不起来**；
- 而读 `PositionLiquidated` 事件**只需要已部署的合约**，今天就能用，Bot 来了也照样用。

对外的诚实说法是：**Bot 带来的不是能力，是吞吐量**。

**两个刻意的细节**：

1. **按基点增量调价**（`bumpPrice`），不是设绝对值——面板不需要知道当前价就能移动它，
   因此读到的过期价格不会把价格送到意料之外的地方。
2. **一次批量调用**清算所有 id，不是循环。合约对整批做**单一价格快照**且**逐笔容错**，
   所以单笔赏金付不出不会拖垮整批——这正是一次交易而非二十次的原因。

**同时补了前端 ABI 缺失的两个事件**：`PositionLiquidated` / `PositionClosed`。
合约里有（`PositionManager.sol:598`）、接口里有（`IPositionManager.sol:46`），
**前端 ABI 里没有**——所以大屏此前读不到任何清算记录。

## 新增 2：`DemoRehearsal.ts` —— 把彩排变成测试

复现 `demo-seed.ts` 的定容与参数，然后**照着操作员的动作跑一遍**：
建仓 20 笔（14 多 / 6 空）→ 调低 15% → 一次批量清算。

| 用例 | 断言 |
| --- | --- |
| 全流程 | 20 笔全部开出；调价后**恰好 14 笔多头可清算、6 笔空头幸免**；批量调用后**剩下的正是空头** |
| 序列即断言 | 批量在**≤2 个区块**内完成——若将来有人把它改成循环，"1 秒内"的宣称会静默失效 |
| 定容失误要响 | 池子过小时 `InsufficientPoolCapacity` **拒绝开仓**，而不是产出付不出的账本 |
| 资金费时钟（见下） | 把演示的**时间预算测量出来**，而不是凭记忆 |

**过程中修了我自己的一个 off-by-one**：`openPosition` 用 `++nextPositionId`，
20 次开仓后计数器读 20，合法 id 是 **1..20 闭区间**；我按 `< next` 循环，静默漏掉最后一笔。
`PositionPanel` 用的是 `<=`——抄错了。已在测试里写明这个坑。

## ⚠️ 本次最重要的发现：演示自带一个 42 分钟的时钟

`demo-seed.ts` 把资金费率设成**上限 1e13**（为了让资金费机制在演示长度内可见，这是对的）。
代价是**拥挤侧会自己流血**，不需要任何价格变动。实测数字：

```
50x · 净抵押 999 → size 49,950 USD
skew +0.4（14 多 / 6 空）
资金费 ≈ 0.1998 USD/块
维持保证金 = 1% × 49,950 = 499.5 USD

→ 约 2,500 块，1 秒出块下约 42 分钟
```

**42 分钟后，多头不用人碰价格就已经可清算。**

对几分钟的演示：**没问题，甚至有用**（不用调价就能展示资金费）。
对**卡住的**演示：**头寸会在主讲人讲话时自己悄悄清掉**，掉出屏幕。

这条已写进测试的**测量用例**并打印到日志，让操作员能直接读出预算；
同时断言 ≥500 块，这样将来改 seed 的参数把预算压没时会失败。
