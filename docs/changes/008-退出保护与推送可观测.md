## GAP-07：`closePosition` 增加 `minOutUsd` 与 `deadline`

### 问题

平仓的成交价是**交易上链时预言机报的价格**，没有调用者约束。在公开 mempool 上这意味着：

- 一笔平仓可以被**扣留**，直到价格变得对调用者不利再被打包；
- 在 Pyth 路径上更直接——价格来自调用者自带的 `pythUpdateData`，
  **执行价完全由提交者选择**。

`IPriceOracle` 其实**返回**了 `publishTime`，但 `PositionManager` 在所有调用点都用
`(uint256 price, )` 把它丢弃了（`:148`、`:191`、以及 `liquidate` 内的取价）。

### 修复

平仓的应收额就是调用者想保护的东西，所以直接给它一个下限：

```solidity
function closePosition(
    uint256 positionId,
    uint256 minOutUsd,   // 应收下限，18 位 USD；0 = 不设保护
    uint256 deadline,    // 超时拒绝；0 = 不设
    bytes[] calldata pythUpdateData
) external
```

**两个检查都在任何状态变更之前**，所以被拒的平仓让头寸**原样保持 open**，
而不是半结算（这是从 GAP-01 学到的：先改状态再 revert 会污染）。

**下限比对的是"截断后可支付"的数额**，不是截断前的：
比截断前会让最多差一个 USDC 单位的平仓通过，破掉下限的语义。

**`minOutUsd` 取 `_payableUsd` 之后的值**——这才是交易者实际收到的数。

### ⚠️ 这破坏了一个冻结接口（必须显式记录）

`推进方案.md:40` 把 `closePosition(uint256, bytes[])` 定为**冻结**，
目的是让前端与（当时尚未开始的）Go Bot 能并行开发。

**现状核查**（`git grep closePosition`）：

**因此代价为零**——没有任何外部消费方。但冻结被破了，所以：

- `IPositionManager.sol` 的 natspec 里**明确写出**"这是对一个曾冻结接口的变更"，
  并说明为什么可以改（未部署、无外部消费方）；

## GAP-08：价格推送改为类型化调用 + 失败可观测

### 问题

```solidity
(bool ok, ) = priceUpdater.call(
    abi.encodeWithSignature("updatePriceFeeds(bytes[])", pythUpdateData)
);
ok; // deliberately ignored
```

三处隐患：

1. **字符串签名**：若与适配器实现的签名漂移，选择器会打空函数而**静默 miss**——
   不 revert、不发事件、链上无痕迹。唯一守护是一条断言计数器变化的测试。
2. **`ok` 被显式丢弃且不发事件**：推送失败（地址错、MON 余额耗尽、update 格式错）
   调用者**完全无信号**——交易成功，只有价格静默地变旧。
3. 参数编码靠手写字符串，绕过了类型检查。

### 修复

改用 `IPyth(updater).updatePriceFeeds(...)`，并补两个事件：

| 事件 | 含义 |
| --- | --- |
| `PricePushSucceeded(updater, updateCount)` | 推送成功——**唯一的正向证据**说明预言机的时效窗口在被刷新 |
| `PricePushFailed(updater, updateCount)` | 推送被吞掉——交易仍继续，但**这次是在一个没人刷新的价格上继续的** |

命名与 `PythOracleAdapter.PricePushed` 区分开：那个说"Pyth 接受了更新"，
这个说"PositionManager 转发了更新"。

### ⚠️ 修复过程中引入又修掉的一个真实回归

第一版**只**做了类型化调用。实测立刻红了：

```
ContractFunctionExecutionError: The contract function "closePosition" reverted
Transaction reverted: function call to a non-contract account
  PositionManager._pushPrices (contracts/perp/PositionManager.sol:556)
```

**类型化调用打到无代码地址时会 revert，而这个 revert 不被 `try/catch` 捕获**
（代码存在性检查发生在调用之前，不在调用内部）。

后果：**一个配错的 `priceUpdater`（EOA、打错的地址）会让每一笔平仓和清算 revert**
——**这就是 GAP-01 换了一条路重新出现**：平不掉的头寸。

旧的低级 `call` 反而不会这样（它把失败包成 `ok = false`），所以这是**类型化带来的新风险**。

**修复**：加 `updater.code.length == 0` 守卫，降级为"跳过推送 + 发事件"。
这正是 `PythOracleAdapter` 构造函数里早就用过的同一个守卫
（那段注释写着"Both guards are needed"——同一个坑，第二次踩）。

**这条值得单独说**：`try/catch` 不捕获"目标无代码"，是一个容易反直觉的 EVM 行为。
现在写进了 `_pushPrices` 的注释，并有一条明确断言"坏 updater 不得卡死平仓"的测试。

## 新增/变更测试

| 测试 | 断言 |
| --- | --- |
| `Refuses a close whose payout falls below minOut` | 低于下限 revert，且**头寸保持 open** |
| `Allows a close whose payout meets minOut` | **恰好等于**下限可以通过（守卫是 `<` 不是 `<=`） |
| `Refuses a close one wei below the floor` | 高 1 wei 必须 revert——**这一条才把 `<` 和 `<=` 区分开** |
| `Treats a minOut of zero as no protection` | `0` = 不设保护 |
| `Refuses a close past its deadline` | 过期 revert，头寸保持 open |
| `Treats a deadline of zero as no deadline` | `0` = 不设 |
| `Accepts a close well inside its deadline` | 正常通过 |
| `Does not block a close when the price updater is not a contract` | 坏 updater 不卡死平仓，**且发出 `PricePushFailed`** |
| `Emits PricePushSucceeded when a push reaches the updater` | 成功路径有正向证据 |

> 边界测试需要**让资金费中性化**（先用另一个账户开等额空单压平偏斜），
> 否则"恰好等于下限"会被几个 wei 的资金费打破。
> 理由写在测试注释里——这是本轮反复出现的模式。

**受影响的既有测试**：14 处 `closePosition` 调用点全部更新为 `[id, 0n, 0n, []]`
（不设保护），语义不变。

## 未竟

- **接口未重新冻结**（新增 GAP-34）。`closePosition` 的签名现在有 4 个参数且**标注为可再变**。
  若 Go Bot 接链时要并行开发，需要先重新冻结并更新 `推进方案.md:40`。
- `liquidate` **未加** `minOut`/`deadline`：清算者拿到的是抵押品的固定比例赏金，
  与被清算头寸的成交价无关，所以没有同类暴露。但**被清算者**无法拒绝一次不利的清算
  ——这属于清算机制本身的设计（无法清算的头寸会卡死，见 GAP-01），不是本条的遗漏。
