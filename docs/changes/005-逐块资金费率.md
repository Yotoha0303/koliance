## 为什么做这个

Metropolis Track 1 官方样例原句含 **"perpetuals whose funding refreshes each block"**，
`前沿资讯与竞品分析.md:294` 判断这是"剩下的空位"——别的链做不了（资金费率通常 1h/8h 一次）。

代码侧实测：perp 合约**完全没有资金费**，但 `Position.openedAt` **只写不读**
（`PositionManager.sol` 唯一出现处是赋值）——预埋字段已存在。

设计理由、备选方案与被否理由见 `docs/adr/ADR-003-逐块资金费率.md`。

## 实现

### 累积（索引法，O(1)）

```solidity
delta = elapsed × fundingRatePerBlockWad × skewWad / WAD
skewWad = (longOI − shortOI) / (longOI + shortOI) × WAD
```

- `cumulativeFundingIndex[feedId]`：按块累加，**惰性**——哪笔交易先碰这个 feed 就先累积。
  无 keeper、无定时器，**链自己的出块就是时钟**。
- 同块幂等（`last == block.number` 直接返回），所以每个入口都调它也只收一次。
- 首次触碰只播种时钟，不从创世块累积（否则索引会等于链高 × 速率）。

### 结算（O(1)）

`Position` 新增 `entryFundingIndex`，应付额
`signedSize × (indexNow − entryFundingIndex) / WAD`，与经过多少块无关。

### 符号约定（**本次实现中真实犯过的错**）

```
index 上升 ⟺ 多头占优 ⟺ 多头付费
signedSize = +size（多）/ −size（空）
正数 = 交易者付
```

第一版写成 `size × delta`（无侧向符号），结果**两侧被收同样的费、空头永远收不到钱**——
资金费变成了手续费而非两侧之间的转移。被 `Funding.ts` 的
`charges the crowded side and pays the thin side` 用例抓到（断言 `short must be paid` 失败）。

### 进入清算判定

`_isLiquidatable` 的权益改为 `collateral + pnl − funding`，**再**截断到 0。

含义：**满偏斜一侧可仅因持仓成本被清算**，价格不动也爆。这是逐块资金费真正"咬人"的地方。

**第二个真实犯过的错**：第一版写成 `pnl − funding`，**漏了 collateral**，
导致权益凭空少一个抵押品。被 `Pays a winning long out of the pool` 抓到
（期望 `11106891000`，实得 `10108888003`）。顺序必须严格是
`collateral + pnl − funding` → 再截断；先截断 pnl 再减 funding 会让 funding"复活"破产头寸。

### 速率是参数，不是常量

**算术事实**：现实速率 `1e11 WAD/块` 对 9,990 USD 头寸是 **0.001 USD/块**——
准确，但几百块的演示里完全看不见。于是存在真实两难：

| 选择 | 后果 |
| --- | --- |
| 现实速率 | 演示里纹丝不动，评委看不到机制 |
| 演示速率 | 好看但是假的 |

**解法：不选，变成参数。** 默认 `1e11`（现实值，诚实），
owner 可在 `[0, 1e13]` 内调整（`MAX_FUNDING_RATE_PER_BLOCK_WAD` 硬上限）。
`demo-seed.ts` 调到上限 `1e13` 让演示可见。机制相同，只有算术尺度不同。

上限的意义：让"演示档"不能变成"抽干抵押品"。治理应**收紧**它，不是放宽。

## 新增接口

| 成员 | 说明 |
| --- | --- |
| `cumulativeFundingIndex(bytes32) → int256` | 每 feed 的累积索引 |
| `fundingRatePerBlockWad() → int256` | 公开状态变量（非函数，故与接口声明一致） |
| `fundingSkewWad(bytes32) → int256` | 当前偏斜，供前端显示 |
| `openInterest(bytes32) → (uint256, uint256)` | 多空未平仓名义 |
| `accrueFunding(bytes32) → int256` | **无许可**累积 |
| `fundingOwed(uint256) → int256` | 只读，**投影到当前块**（读 storage 会返回 0） |
| `positionEquity(uint256) → int256` | 含资金费的权益，即 `_isLiquidatable` 实际比较的值 |
| `setFundingRatePerBlockWad(int256)` | onlyOwner，有上限 |
| event `FundingAccrued(feedId, index, blockNumber, skewWad)` | 带块号，可证明逐块 |
| event `FundingSettled(positionId, amount)` | 正数 = 交易者付 |

**命名注意**：权益 getter 叫 `positionEquity` 而非 `equity`——
所有结算路径都有名为 `equity` 的局部变量，Solidity 会对遮蔽发警告。

## 受影响的既有测试（已同批修改）

资金费进入判定后，5 个既有用例的数值/语义不再成立。**改动方式一律是「让资金费中性化」，
不改判定逻辑**：

| 用例 | 改动 | 理由 |
| --- | --- | --- |
| `Is liquidatable exactly at the computed liquidation price` | 先开等额空单压平偏斜 | 断言的是 PnL 边界，funding 会移动阈值使 ±1 wei 断言失去意义 |
| `Is not liquidatable one wei above the liquidation price` | 同上 | 同上 |
| `Refuses to liquidate a healthy position` | 同上 | 同上 |
| `Pays a winning long out of the pool` | 用**另一个账户**的等额空单对冲 | 不污染交易者余额（用同一账户会改变断言基数） |
| `Leaves a losing long's remainder in the pool` | 同上 | 同上 |

理由写在测试注释里。资金费本身由 `test/perp/Funding.ts` 的 18 条覆盖。

## 新增测试

### `contracts/test/perp/Funding.ts`（18 条）

| 性质 | 用例 |
| --- | --- |
| 平衡账本不再累积 | `accrues nothing further when long and short open interest are equal` |
| 平衡后双方义务不增长 | `stops growing either side's obligation once the book is balanced` |
| **拥挤侧付、稀薄侧收** | `charges the crowded side and pays the thin side` |
| 偏斜反向则方向翻转 | `flips direction when the book turns short-heavy` |
| **逐块**（与块数成正比） | `advances the index in proportion to the number of blocks elapsed` |
| 同块幂等 | `is idempotent within a single block` |
| 首次触碰不追溯创世块 | `does not accrue from the genesis block on a feed's first touch` |
| 多 feed 独立 | `keeps feeds independent` |
| 平仓时结算并减少赔付 | `settles accrued funding on close, reducing the payout` |
| 平仓后停止计费 | `stops charging a position once it is closed` |
| **仅凭资金费即可清算** | `can push a position through its maintenance margin on its own` |
| 默认速率是现实值 | `starts at the realistic default` |
| 速率上限生效 | `lets the owner retune the rate, and refuses one above the ceiling` |
| 权限 | `refuses a rate change from anyone but the owner` |
| 零速率不累积 | `accrues nothing at a zero rate` |
| **无许可累积** | `lets anyone accrue funding, not just the owner` |
| 事件带块号 | `emits FundingAccrued carrying the block number` |
| 结算事件 | `emits FundingSettled when a position settles` |

**关键的一条**：`can push a position through its maintenance margin on its own` ——
50x 多单、价格**完全不动**，1,500 块后权益跌破维持保证金、`isLiquidatable` 返回 `true`。
这直接证明"仅持仓成本即可爆仓"，即逐块资金费相对 8 小时费率的核心差异。

## 前端：改为**读链**而非镜像

`PositionPanel` 原先本地算 `unrealizedPnl` / `marginRatioBps` / `isLiquidatable`。
资金费进入判定后，本地算会与链**在最关键的时候分歧**——拥挤侧被持仓成本挤压时。

因此改为读链上 getter（`positionEquity` / `fundingOwed` / `isLiquidatable`），
并在持仓行新增**资金费**与**权益（含资金费）**两列。

仍保留镜像的只有**预估强平价**——链上没有 per-position getter，由
`tests/perp.test.ts` 的 bit-for-bit 用例守着。这条限制写在组件注释里。

---

## `demo-seed.ts` 的一处重要修正

原种子脚本用 `i % 2 === 0` 开仓 → **10 多 10 空，偏斜恰好为 0**，
资金费一分钱不累积。**同一个 50/50 混合既让批量清算好看，也让资金费隐形。**

改为 `LONG_COUNT = 14`（14 多 6 空，偏斜 +0.4）：
多头付费、空头收钱，且**价格下跌时仍清算多头、放过空头**——两个机制都可见。

实测：
```
openInterest    : long 699300 / short 299700 USD
fundingSkewWad  : 400000000000000000 (+0.4000)
invariant       : totalAssets >= reservedAssets  OK
```

脚本还会在偏斜为 0 时**打印提示**，避免下次有人重新踩这个坑。
